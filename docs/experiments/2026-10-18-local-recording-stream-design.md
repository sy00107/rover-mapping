# Pi 원본 기록과 실시간 전송 분리 검토

기본 촬영 경로에 구현했다. 기존 터미널 명령과 시작/종료 조작은 유지한다.
아래 설계의 실제 카메라·무선·SD 동시 부하 검증은 아직 하지 않았다.
연결 내성·복구 후속 보완은 [구현 기록](2026-10-18-capture-resilience.md)을 따른다.

## 적용한 동작

- `controller.py`는 실제 촬영 시작 시 기존 배포 기능으로 코드를 Pi에 보낸 뒤
  `local_client.py`를 실행한다. 합성 데모 및 별도 worker 입력 경로는 유지한다.
- Pi 원본 경로는 `/home/pi/handheld_mapping/recordings/RUN_ID`다.
  `local_recording.py`의 독립 세션 프로세스가 카메라 출력을 `capture.bin`에
  무손실 packet 형식으로 보관한다. 2초마다 fsync하며 원본 기록 큐는 32 MiB로
  제한한다. 큐 누락은 계측에 남고 최종 결과를 일부 누락 상태로 처리한다.
- 원본은 stream별로 즉시 기록한다. 깊이 영상이 안 와도 좌우 원본이 보존된다.
  네트워크·미리보기 처리 경로는 원본의 송신 목적지가 아니다.
- IMU 함께 기록이 켜져 있으면 기존 SPI 브리지의 UNIX tee를 Pi에서 구독하여
  `imu/RUN_ID`에 보정·원시 telemetry·시각·보정 파일·URDF·요약을 저장한다.
  Pi 기록 시각을 노트북 수신 시각으로 표시하지 않는다. SPI 소유권은 추가로 얻지 않는다.
  브리지도 Pi의 독립 supervisor로 실행한다. SSH 로그 창 종료는 브리지 종료가 아니다.
- 미리보기는 최신 좌우 쌍의 320×240 JPEG quality 65이며, 깊이는 최대 2 FPS의
  무손실 320×240 Z16이다. 좌우 쌍 생성은 depth를 기다리지 않는다.
  깊이를 보낼 때는 2 ms 안의 대응 시각만 사용한다. 기록 원본은 640×480/15 FPS다.
  영상 축소 방식에 맞게 미리보기 내부 파라미터도 조정한다.
- 별도 스레드가 최신 미리보기 snapshot만 교체한다. SSH는 해당 snapshot과
  기록 FPS·누락 계측·디스크 여유·IMU 상태를 읽는다. SSH EOF는 원본 종료 조건이 아니다.
  노트북에서 연결 복구 대기를 표시하고 재연결한다. 단절 중 Pi의 현재 상태를
  실시간으로 확인할 수는 없다.
- 노트북 미리보기는 `RUN/preview`에만 저장한다. 최종 원본의 calibration과
  `frames.jsonl`을 공유하지 않으며, 최종 ORB 입력에 JPEG 미리보기를 넣지 않는다.
- 종료 요청 후 터미널과 창에 **촬영 종료 · Pi의 영상·IMU 원본을 노트북으로
  옮기는 중입니다. 완료될 때까지 기다려 주세요.**를 표시한다.
  전송률 대신 전송 byte/전체 byte의 진행률을 약 1초 간격으로 출력한다.
- 카메라·IMU의 정상 종료 후 파일별 size/SHA256 manifest를 만든다. 노트북은
  `RUN/pi_originals`의 `.part` 파일에서 이어받고 size/SHA256이 맞은 파일만 확정한다.
  한 파일에서 진행 없는 재연결이 30회 이어지면 실패로 보고 양쪽 원본을 보존한다.
- 검증된 `capture.bin`을 기존 PNG/인덱스 형식으로 풀고 stream별 개수도 대조한다.
  IMU 원본은 같은 RUN의 기존 파일명으로 복사한다. 이 과정 이후에만 최종
  ORB·중력·TSDF·선택형 IMU 후처리를 실행한다. Pi 원본은 [검증 후 정리 정책](2026-10-18-recording-retention.md)에 따라 최신 촬영과 미검증·이상 촬영을 남기고, PC 원본을 다시 확인한 과거 촬영만 정리한다.
- Pi 저장공간이 512 MB 미만이면 원본 촬영을 종료한다. IMU 기록 중단은 기본적으로
  영상 기록과 분리하고 누락 구간 및 부분 성공으로 남긴다. 명시적 strict_imu 설정만
  IMU 실패 시 전체 종료한다. 로컬 저장 자체의 실패를 미리보기 오류로 숨기지 않는다.
- 좌우 시각 매칭률, 깊이 대응률, 영상 시각/순번 공백을 별도로 검사한다.
  전송 체크섬 검증 성공을 촬영 무누락으로 해석하지 않는다.

## 실행과 복구

기존 `bash tools/handheld_mapping.sh` 또는 현장 수집 명령을 그대로 사용한다.
이미 켜 둔 앱은 종료 후 새로 실행해야 새 코드를 사용한다. IMU 브리지 터미널에서
로그를 볼 수 있다. Pi 배포는 다음 실제 촬영 시작 시 자동 실행된다.
새 브리지는 Ctrl+C로 로그 창만 닫히며, 종료는 다음 명령을 사용한다.

```bash
bash tools/mapping_imu_bridge.sh pi@raspberrypi.local --stop
```

전송이 실패해 앱 세션이 끝난 경우, 아래 명령으로 원래 Pi 세션을 정지하고
새 폴더 또는 checkpoint가 있는 원래 촬영 폴더에 원본을 가져올 수 있다.
`RUN_ID`와 host를 해당 촬영 값으로 바꾼다. 기존 폴더는 checkpoint의 host/ID가
맞을 때만 이어받으며, 이미 정리된 PNG/인덱스도 검증하고 재사용한다.
복구 명령은 원본 가져오기만 수행한다. 앱의 '중단된 원본 이어받기'는 최종 지도 계산까지 진행한다.

```bash
PYTHONNOUSERSITE=1 .venv-mapping/bin/python -m experiments.handheld_mapping.local_client \
  --recover --host pi@raspberrypi.local --run-id RUN_ID \
  --run outputs/handheld_mapping/recovered/RUN_ID
```

Pi 정상 종료/전원 차단은 원본 촬영의 연속성을 보장하는 경우가 아니다.
촬영 종료 및 전송 완료 안내를 확인한 후 정상 종료한다.
재부팅으로 RAM 배포 코드가 사라진 경우의 복구 실행 경로는 이번 범위에서 보류했다.

## 검증 기록

- 전체 handheld 매핑 회귀: **496 passed, 9 skipped (59.38초)**.
  이후 독립 프로세스 시작/중복 시작 회귀를 추가한 관련 경로 검증도 **15 passed**.
  Python compileall, 변경 Python의 pyflakes 및 `git diff --check`를 통과했다.
- 로컬 실제 subprocess로 미리보기 연결 종료 후에도 영상·IMU 기록이 계속됨을 확인했다.
  depth가 없는 프레임의 좌우 원본도 보존되고, IMU 시각은 Pi 기록 시각으로 남는다.
- 전송 중단 후 offset 이어받기, SHA256 불일치 시 확정 거부, 재연결 때 미리보기
  calibration/영상 중복 제외, 최종 원본과 미리보기 분리 및 계산 순서를 검증했다.
- 기존 실제 RUN `20261015_152413_6fea4a`의 연속 60쌍을 새 미리보기 형식으로
  15 FPS 재생하여 native ORB 처리 60쌍, tracking state=2, dropped_pairs=0,
  map_changes=0, observed_cells=261을 확인했다. 마지막 프레임 처리 약 10.29 ms.
  이는 짧은 기존 영상 재생 결과이며 현장 무선·Pi CPU·SD 기록 성능의 검증은 아니다.
- Pi SSH로 저장공간 약 13 GB와 OpenCV 4.6.0 존재만 확인했다.
  새 실기 촬영 및 모터 명령은 실행하지 않았다.

## 확인한 근거

- 대상: `outputs/handheld_mapping/sessions/20261018_124046_846cdc/session.json`.
- 약 382.55초 동안 left received=5743, enqueued=367, dropped=5375.
- 전송 payload 약 160.62 MB, 촬영 시간 기준 약 3.36 Mbps. 이는 해당 실행의
  애플리케이션 처리량이며 Wi-Fi 링크 최대 속도나 순수 네트워크 대역폭 측정값이 아니다.
- 전송 쓰기 누적 약 372.33초, 압축 누적 약 9.96초. 노트북 수신 버퍼 drops=0.
- 전송된 묶음의 평균 크기로 15 FPS를 추정하면 약 52.5 Mbps가 필요하다.
- 현재 `pi_worker.py`는 left/right/depth 세 장을 모두 모아야 송신 큐에 넣으며,
  큐 부족 시 세 장을 모두 버린다. `controller.py`는 작업 폴더를 `/dev/shm`에 만든다.
- SSH stdin EOF, SIGHUP, 송신 오류가 촬영 종료로 이어진다. 저장 위치만 바꿔도
  무선 단절 후 촬영이 계속되는 구조가 되지는 않는다.

## 권장 구조

1. Pi의 카메라 입력에서 원본 기록과 실시간 송신을 별도 경로로 분기한다.
   원본 기록을 네트워크 큐 뒤에 두지 않는다. 좌/우 mono8와 depth Z16을
   무손실로 저장하고 timestamp, 시퀀스, 보정값, 카메라 metadata 및 IMU를
   함께 보존한다. 현재 IMU도 SSH를 통해 노트북에 기록하므로 로컬 기록을 추가해야 한다.
2. 원본은 RAM 디스크와 분리한 영구 저장장치에 청크 단위로 기록한다.
   무압축 payload는 18.432 MB/s, 분당 약 1.106 GB이며 인덱스 등 부대 용량은 별도다.
   실제 Pi 저장장치의 지속 쓰기 속도와 압축 CPU 부하를 측정해 형식을 정한다.
   기록 큐도 유한하게 두고 포화·디스크 부족을 기록 오류로 표시한다.
3. 원본 기록 프로세스의 수명을 SSH 세션과 분리한다. 명시적 시작/정지,
   상태 조회, 통신 단절 표시, 저장공간 감시를 제공한다. 전송 오류는 원본
   촬영 종료 조건에서 분리하고, 네트워크 복구 뒤 상태 및 전송을 재개한다.
4. 실시간 송신은 같은 timestamp의 좌우 쌍을 하나의 단위로 다룬다.
   depth는 별도 큐로 보내며 stereo가 depth 도착을 기다리지 않게 한다.
   depth 전송이 이미 쓰기를 막고 있으면 큐 우선순위만으로 해결되지 않으므로,
   depth 패킷 크기·전송률 제한 또는 별도 연결을 함께 검토한다.
5. 좌우는 시간적 연속성을 우선해 15 FPS 유지를 목표로 압축·해상도를 비교한다.
   JPEG는 실시간 복사본에만 시험하며 원본과 다른 경로·용도로 표시한다.
   해상도 변경 시 내부 파라미터와 추적 설정도 함께 조정한다.
6. 실시간 depth는 우선 2~5 FPS 후보로 비교한다. 해당 depth와 정확히 대응하는
   pose가 있을 때만 관측 색을 갱신한다. depth가 없는 영상은 pose 추적만 갱신하며,
   오래된 depth를 현재 pose에 붙이지 않는다. 현재 2 ms 대응 기준을 임의로 늘리지 않는다.
7. 촬영 종료 후 원본을 재전송·이어받기하고 파일 수·시퀀스·체크섬을 검증한다.
   최종 ORB/지형 생성은 동기화한 원본으로 수행하며 실시간 미리보기 결과와 구분한다.

## 전송량 간이 비교

같은 RUN에서 stream마다 시간순으로 고르게 20장을 선택해 노트북에서 재압축했다.
아래는 payload 크기만으로 계산한 15 FPS 추정값이다. Pi 인코딩 성능,
전송 지연, 추적 정확도는 측정하지 않았다.

| stream | 현재 zlib level 1 | JPEG quality 80 후보 |
|---|---:|---:|
| left | 17.57 Mbps | 2.26 Mbps |
| right | 18.15 Mbps | 2.43 Mbps |
| depth | 16.85 Mbps | 사용하지 않음 |

depth를 전혀 보내지 않아도 현재 무손실 stereo만 약 35.72 Mbps다.
JPEG stereo도 약 4.69 Mbps로 해당 실행의 처리량 3.36 Mbps보다 크다.
JPEG stereo 15 FPS + 현재 방식 depth 2 FPS는 약 6.94 Mbps다.
따라서 depth 빈도 조정이나 JPEG 하나만으로 해결된다고 가정할 수 없다.
더 작은 실시간 영상과 전송 경로 개선을 함께 비교해야 한다.

## 구현 및 검증 순서

1. 원본 로컬 기록과 가져오기부터 구현해 무선 송신 차단 시험을 한다.
   입력 수·기록 수·시퀀스 공백·기록 큐 포화·복구 뒤 읽기 및 체크섬을 대조한다.
2. 좌우 쌍 전송을 depth 대기에서 분리하고 실제 수신 FPS·최대 영상 공백을 측정한다.
3. 동일 원본으로 무손실, JPEG, 해상도 후보를 재생해 추적 손실·맵 분리·궤적을 비교한다.
   이후 Pi 실기에서 기록과 인코딩을 동시에 돌려 CPU·디스크·지연을 검증한다.
4. 추적 손실률과 맵 분리가 줄어드는지 같은 동선의 현장 기록으로 확인한다.

원본 보존과 실시간 추적은 별도 성공 조건이다. 로컬 원본이 완전해도
미리보기는 통신 단절 때 멈출 수 있고, 영상 자체의 질감 부족·흔들림 때문에
원본 재생에서도 추적이 실패할 수 있다.
