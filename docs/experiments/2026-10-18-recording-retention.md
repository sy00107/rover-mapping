# Pi 원본 자동 정리와 최신 촬영 보관

영상과 IMU 원본을 PC에 전송한 뒤 검증된 과거 촬영 폴더만 Pi에서 정리한다. PC 원본은 삭제하지 않는다. 정상적으로 전송된 촬영만 있을 때 Pi에는 최신 촬영 한 개가 남는다.

## 삭제 승인 조건

1. 촬영 ID와 Pi 원본 경로가 일치하고, 정상 종료된 manifest가 있어야 한다. 복구 촬영, 오류 촬영, IMU 기록 이상은 보존한다.
2. PC의 `pi_originals`에 manifest에 기재된 영상·IMU·로그 파일이 모두 있어야 한다. 파일마다 정확한 크기와 SHA-256을 확인한다. `.part`나 PNG/지도만 남은 폴더는 원본 수신 증명이 아니다.
3. 영상 아카이브의 모든 packet과 압축 영상을 읽고 보정값, 정상 종료, 좌·우·깊이 프레임 수를 확인한다. JSON/JSONL도 끝까지 읽는다. 비정상 종료 복구본은 유효 prefix 밖의 바이트가 남아 있을 수 있으므로 자동 삭제하지 않는다.
4. PC 원본 파일과 manifest를 `fsync`하고 원본 폴더부터 출력 루트를 포함한 모든 상위 폴더의 디렉터리 항목까지 동기화한다. 실패하면 삭제하지 않는다.
5. PC의 `.pi_verified_copies`에 촬영별 전송 증명을 저장한다. 과거 증명만으로 삭제하지 않으며, 정리할 때 과거 PC 원본도 다시 읽어 검증한다. 이전 앱의 촬영은 같은 저장 루트에 host/촬영 ID가 일치하는 `transfer_checkpoint.json`과 완전한 원본이 있을 때만 새 증명으로 승격한다.
6. Pi에서도 manifest와 전체 원본의 크기·SHA-256을 다시 검사한다. 명시된 크기 뒤에 바이트가 더 있거나 목록에 없는 파일/링크가 있으면 보존한다. supervisor/자식 프로세스가 살아 있거나 카메라 종료 확인이 없으면 정리하지 않는다. 촬영별 lock은 recorder와 정리가 공유하며, 정리끼리도 직렬화한다.
7. Pi의 가장 최근 시작 촬영과 가장 최근 검증 촬영은 반드시 남긴다. 최신 촬영이 아직 미전송이면 마지막 검증 촬영도 추가로 보관한다. 촬영 순서를 확인할 수 없으면 정리를 보류한다.
8. Pi의 `.retention_audit`에 manifest와 PC 증명·보관 대상·삭제 대상 이력을 디스크에 확정한 뒤 `.verified_trash`로 폴더를 원자적으로 이동하고 제거한다. 중간 중단으로 휴지통에 데이터가 남으면 자동 재삭제하지 않는다. PC의 해당 원본과 이력을 확인하여 별도로 정리할 수 있다.

## 동작과 제한

- 검증 단계는 디스크 전체 읽기와 영상 디코딩을 추가하므로 전송 완료 후 시간이 더 걸린다. 앱에는 원본 검증과 Pi 정리 상태가 표시되며 전송 보류 버튼으로 중단할 수 있다.
- 연결 단절/정리 실패는 지도 생성을 실패시키지 않는다. PC 촬영 폴더의 `pi_retention.json`, `transfer_checkpoint.json`, `session.json`에 결과를 남긴다. 응답이 끊기면 Pi에서 정리가 일부 완료됐을 가능성은 있으나, 승인된 원본은 이미 PC에서 검증·동기화된 상태다.
- 미전송, 손상, 중단, IMU 이상, PC 복사본을 확인할 수 없는 촬영은 삭제하지 않는다. 따라서 예외가 있으면 Pi에 한 개보다 많이 남는다. 저장 공간 부족을 이유로 미검증 원본을 강제로 삭제하지 않는다.
- PC 원본을 사용자가 삭제/이동했거나 다른 저장 루트로 바꾼 경우 기존 증명만으로 Pi 원본을 지우지 않는다.
- 기존에 보류한 재부팅 후 임시 실행 코드 유실 문제는 별개다. SSH/실행 코드가 없어 정리 요청을 수행할 수 없으면 보존한다.
- `fsync`와 체크섬은 운영체제/저장장치가 정상적으로 보장하는 범위의 저장을 확인한다. 향후 PC 디스크 자체 고장까지 막는 이중 백업 정책은 아니다.
- 실제 Pi에는 아직 연결하지 않았다. 기존 Pi 데이터 삭제도 실행하지 않았다. 다음 촬영의 코드 배포부터 적용되며 실행 중인 앱은 재시작한다.

## 검증

임시 디렉터리에서 실제 파일·원본 packet·압축 데이터·SSH 대체 Python subprocess CLI를 사용한다. 8방향 조종과 기존 촬영/복구 기능의 회귀 검사도 함께 수행한다. 실제 카메라/SPI/모터는 사용하지 않는다.

포함 시나리오: 최신 촬영 보관, 미전송 보관, 과거 PC 복사본 손상/누락/부분 파일/링크, 현재 영상 손상/압축 오류/IMU 미완성/프레임 수 불일치, Pi 원본 변경/추가 바이트/미기재 파일, 실행 중 프로세스/촬영 lock, fsync 실패, 정리 연결 끊김과 재시도, 삭제 중단 시 감사 이력과 휴지통 잔존, 취소, 구버전 전송 폴더 검증, 보관할 최신 Pi 복사본 손상, 촬영 순서 불명, 실제 transport의 전송→import→정리 연계.

실행 결과: 전체 회귀 577 passed / 9 skipped (80.73초). 이후 최종 저장 경로 동기화·manifest 링크 방어를 포함한 정리 안전성 34개 전부 통과 (12.32초). 앱과 정리 연계 검사 53개 통과. pyflakes 및 `git diff --check` 통과. 로그와 실제 Qt 렌더는 `outputs/handheld_mapping/reviews/recording_retention_20261018/`에 저장했다.

## 별도 전송 터미널

앱에서 **종료 및 지도 생성** 또는 기존 촬영 이어받기로 원본 전송을 시작하면 새 터미널 창이 자동으로 열린다. **전송 창 열기**로 다시 열 수도 있다. 수신 퍼센트·수신/전체 MB·속도·남은 예상 시간을 한 줄에서 갱신하며, 연결 불안정·복구 때만 별도 알림 줄을 남긴다. 터미널 폭에 맞춰 줄바꿈을 방지한다. 100% 이후 영상 정리·원본 검증·Pi 정리 결과를 이어서 표시한다. **100%는 바이트 수신률**이며 최종 검증 완료와 구분한다. 완료/보류/실패 후 창은 Enter를 누를 때까지 남는다.

이 창은 `transfer_status.json`을 읽는 별도 프로세스다. 창 닫기/Ctrl+C는 촬영·전송 프로세스에 명령이나 신호를 전달하지 않는다. 실제 보류는 앱에서 한다. 진행 이력은 촬영 폴더의 `transfer_progress.jsonl`에 남고, 터미널 실행 오류는 `transfer_terminal.log`에 남는다. 터미널/로그 표시 실패는 원본 전송 성공 조건과 분리된다. 송신 프로세스가 죽으면 성공으로 표시하지 않고 확인 불가/이어받기 안내를 표시한다.

터미널 수동 실행:

```bash
PYTHONNOUSERSITE=1 .venv-mapping/bin/python -m experiments.handheld_mapping.transfer_monitor /절대경로/RUN
```
